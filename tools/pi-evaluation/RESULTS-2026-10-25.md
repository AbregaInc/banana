All four runs completed serially with identical fictional prompts and both repeats. All owned workers exited; no app capability executed. Both models were thinking-off, one slot, 32,768 context, 2,048 output cap and a 2 GB cache. Raw reports and server logs are in `docs/research/pi-apple-host-results/eval-qwen35-*`.

**Interpretation:** retain the existing 4B/Locals default. These results do not establish the best possible model/engine. Every run paged; a clean-host repeat is required for a performance ranking. Locals' 4B warm median was lower in this configuration, while 2B used less GPU allocation but failed more task contracts. The stock engine shares the Locals HTTP frontend; it is not a standalone-server sweep.

Manual failure review: 4B made unnecessary read-tool calls for greetings (and one unsupported deletion request). 2B confused new-meal and copy tools, called an event tool without a decided time, and in one Locals run proposed `create_note` despite an explicit no-save instruction. The runner executed none of those intents. Schema/native validation would reject some invalid proposals, but a syntactically valid wrong write is still a quality failure. Do not promote 2B on memory size alone.

The 22-case corpus is development evidence, not held-out accuracy; no-tool scoring is a reply contract rather than a truthfulness/usefulness judge. App history, native work, cold loading, UI publication and long-running thermal/lifecycle conditions require the separate real-app promotion gate. GPU peaks and RSS overlap; neither is certified total app footprint. The current real-app 4B workspace reports include a slow 99.54-second meal turn on the loaded host, so do not promise subsecond app-wide performance from this table.
