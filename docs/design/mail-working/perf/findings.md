- First frame `root.appear` ≈ 940 ms shell, 1,251 ms populated Day, 1,311 ms Week (iPhone; iPad +50 ms); ~225 ms of `@StateObject` construction on the first render.

- Noise floor: `root.appear` ±39 ms at equal load; host-load swings (8→412) shift every mark +80–120 ms uniformly, so `compare` normalises by `app.init.body` (mark ratios stable ±0.05); `*.loaded` ±68 ms → 100 ms floor; idle CPU ±0.

- Most at risk from mail: background-playback CPU (§5 row 1), launch (`root.appear`), backgrounded-idle "no timers alive" (already broken).

## HIGH
**F1 — Synchronous `locationd` XPC inside a `@StateObject` constructor, first-render path.** Pre-existing, missed by §4b. MEASURED: `sample` of the stuck process (`logs/smoke-sample.txt`): 1,595/1,595 main-thread samples in `OnboardingStore.init() → OnboardingStore.swift:35 → CoreLocation → __NSXPCCONNECTION_IS_WAITING_FOR_A_SYNCHRONOUS_REPLY__`; journal stops at `⏱ history.init`, no `root.body` for > 40 s on three launches (0.8 s CPU); after `simctl location set` + `privacy grant location` the same launch reached `root.appear` +1,181 ms. READ-IN-CODE: `OnboardingStore.swift:33-39` reads `locationManager.authorizationStatus` and `EKEventStore.authorizationStatus` in `init`; it is a `@StateObject` (`BananaApp.swift:54`) so this runs during first render — the marks prove the order (`app.init.done +745` then `smart.init +829 … history.init +947`; the comment at `BananaApp.swift:88-90` is wrong). Cost: a daemon round-trip before the first frame on every launch; blank until `locationd` answers. Fix: seed from cached values, read the real ones one run-loop turn later (`AlarmStore.swift:83` pattern); construct `EKEventStore` lazily.

**F2 — Full foreground cascade on every `inactive → active`, not only return from background.** Since July (cascade grew: `CloudSyncPoll.resume` 30 Sep, `flushNow("foreground")`, `adoptGoogleAccountsAddedElsewhere`). READ-IN-CODE: `RootView.swift:252` ignores the previous phase; `.active` (:273-301) runs `CloudSyncPoll.resume()` (immediate check = 1 CK request), `CloudProgressSync.flushNow("foreground")` (`reconcileUploads` + send + fetch + zone poll, `CloudProgressSync.swift:181-239`), a keychain read, `smart.recomputeIfStale()`, `onboarding.refresh()`, three authorization re-reads. The `.inactive` comment (:302-310) documents that Control Center, the shade, permission alerts and the switcher all go `inactive → active`. Cost: ≥ 4 CloudKit round trips per glance; a volume change via Control Center mid-episode spends CloudKit (§5 "0 CloudKit" near-miss, user-triggered). Fix: `cameFromBackground` flag set in `.background`, cascade only when set.

**F3 — Fitness CloudKit bookkeeping in UserDefaults as whole-dictionary blobs, swept into the iCloud backup.** Since July (`5ac195f`, 27 Sep). READ-IN-CODE: `CloudProgressSync.swift:1377-1380` `persistBookkeeping()` writes `systemFields` (one archived `CKRecord` per synced workout; comment :1351-1353 counts 333) and `revisions` whole per engine event (:1342); `saveRevisions()` also on every `queue(touchedNow:)`/`queueHealth` (:910, :931) = every `HealthKitStore.persist()`. `CloudBackup.swift:325-333` excludes only `ckSyncEngine.progress.*`, so `ckSyncEngine.fitness.*`/`.settings.*`/`.controls|meals.state` are hashed, uploaded and restored onto other devices — the comment at :321-323 calls that "actively wrong". The F16 class (stamps moved out of UserDefaults in July) reintroduced. Cost (INFERRED): cfprefsd rewrites the whole plist on every set; backup digest churn; foreign engine state restored. Fix: plist on `persistenceQueue` (pattern :622-629); add the four key prefixes to `operationalDefaults`.

**F4 — iPad/Mac Workouts list: a live MapKit `Map` per route row.** Since July (29 Sep). READ-IN-CODE: `WideWorkoutsView.swift:465-479` (`Map` + `MapPolyline` per row in a `LazyVStack`, coordinates re-mapped per body :468-470); the phone deliberately uses `MKMapSnapshotter` (`FitnessView.swift:459-461`: "far lighter in a scrolling list than a live Map per row"). Reached via `RootView.swift:694`. Not the cause of the measured iPad one-off (fixture row has no route). Fix: reuse `RouteSnapshot`/`RouteSnapshotCache`.
