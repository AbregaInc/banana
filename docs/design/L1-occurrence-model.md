# L1 — The Occurrence Model & Write-Back Contract

Status: **design only, not built.** This is the foundation layer (L1) of the unified
timeline. Later layers (L2 exceptions, L3 tasks, L4 flexible scheduler) build on it.

## Locked product decisions

1. **Write-back: yes**, into the user's **existing calendars** (not a dedicated app calendar).
2. **Stickiness:** items are **sticky by default**; flexibility is **opt-in** per item
   (`moveable`).
3. **Reflow:** **manual only** — the flexible scheduler relocates `moveable` items *only*
   when the user taps "Re-plan my day." Nothing auto-shuffles.
4. **What's written:** **everything, including cues** (audio routines write calendar events too).
5. **Hold intent:** written blocks are **Busy** (defend the time; visible to shared-calendar viewers).

### Assumed defaults (correct here if wrong)

- The scheduling/reflow brain runs on the **phone**; results push to the watch.
- **User edits in Calendar always win.** External is the source of truth; the app re-flows
  around manual edits, never overwrites them.
- **Derived items recompute automatically** (wake/wind-down/commute) even under manual
  reflow — that's derivation, not reflow. Their written events update in place.
- Rolling materialization horizon ~**2–4 weeks**; re-armed on any input change.
- Tasks (L3) will bind to **Apple Reminders** via EventKit unless changed.

## 1. The `Occurrence`

Everything on the timeline is one `Occurrence`. Tabs are filters over occurrences, not
separate features.

```
Occurrence
  id            AppItemID          // stable, app-owned; survives calendar round-trips
  seriesID      SeriesID?          // groups a recurring set (for L2 exceptions)
  source        Source             // .external | .derived | .authored
  behavior      Behavior           // .event | .cue | .task | .block
  schedule      Schedule           // when + how it got its time
  writeState    WriteState?        // link to the calendar event this maps to (if written)
  title, icon, color
  cueRef        CueRef?            // attached audio routine, if any behavior carries one
```

`AppItemID` is the anchor of the whole design: it is generated by the app, stamped into
any calendar event we write (see §4), and is how we recognize our own writes on read-back.

### Behaviors and whether they write to the calendar

| Behavior | What it is | Writes a calendar event? |
|---|---|---|
| `.event` | An appointment you attend | No — these ARE external calendar events (we read them) |
| `.cue` | Arms/plays a routine (podcast pool, music, sleep timer, fade) | **Yes** (decision 4) |
| `.block` | Protected time the system reserves (focus, a habit slot) | **Yes** |
| `.task` | A to-do (deadline / unscheduled / placed) | **Yes** once scheduled |

Ephemeral **nudges** ("leave now", pre-workout ping) are *not* occurrences and are *not*
written — they're local notifications derived from an occurrence's time.

### Schedule + the moveable flag

```
Schedule
  mode        .fixed | .derived | .flexible
  anchor      Anchor                // resolves to a concrete time/window
  moveable    Bool = false          // opt-in; only .flexible items can be true
  window      TimeWindow?           // for .flexible: allowed placement range
  constraints Constraints?          // duration, frequency, earliest/latest, priority
```

- `.fixed` — pinned time (meetings, hard commitments). Never moved.
- `.derived` — computed from other occurrences (wake ← first meeting; wind-down ← sleep
  schedule). Recomputes automatically; not subject to reflow.
- `.flexible` — placed by the scheduler into open time. With **manual reflow**, placement
  happens at create-time or when the user taps "Re-plan." Only `moveable == true` items may
  be relocated by a re-plan; sticky flexible items keep their placement.

## 2. Sources → how each produces occurrences

### External (read-only)
- Backed by EventKit; the existing `CalendarService` merge + dedupe is the ingest path.
- Produces `.event` occurrences with `source == .external`, `schedule.mode == .fixed`.
- **On read, any event carrying our `AppItemID` marker is NOT emitted as external** — it's
  reconciled against the authored/derived occurrence that wrote it (see §4). This is what
  prevents the self-ingest loop that "write into existing calendars" would otherwise cause.

### Derived (computed, not stored as input)
- Smart wake (from first meeting), wind-down (from sleep schedule / next wake), commute
  legs. Today's `.earliestMeeting` trigger generalizes into this.
- Recompute whenever inputs change; their **written events update in place** via `writeState`.

### Authored (the user's own)
- Native cues/routines, one-off in-app events, and (L3) tasks.
- A cue **binds to a time-source**: `.clock(recurrence)`, `.calendar(match)`,
  `.sleepSchedule`, `.firstMeeting`, `.workoutStart`. (This is the Option-D generalization:
  Calendar is one source among several; wind-down binds to sleep-schedule, not events.)

## 3. Cue ↔ source binding (the Option-D generalization)

A cue no longer owns a clock; it names a **source binding** + a **timing offset**:

```
CueBinding
  source   .clock(Recurrence) | .calendar(EventMatch) | .sleepSchedule
         | .firstMeeting | .workoutStart
  timing   .atStart | .before(minutes) | .afterEnd(minutes)
```

`EventMatch` (only needed for `.calendar`) is the three-tier router:
1. **calendar scope** — which EKCalendars feed this cue
2. **title match** — keyword/alias list (Gym = {gym, lift, leg day})
3. **local pins** — user taps an event → "Treat as Gym"; stored `eventID → cueID` +
   learned alias. No calendar write needed for corrections.

## 4. Write-back sync contract (the heart of L1, given the locked decisions)

Because we write **into the user's existing calendars**, write-back is a **continuous
create/update/delete sync**, not create-once. Each writable occurrence owns at most one
calendar event.

### Identity / tagging (mandatory)
- Every event we create is stamped with our `AppItemID` in a durable, hidden field
  (event `notes` sentinel and/or `url`), plus the `SeriesID`.
- On calendar read, events bearing our marker are matched back to their owning occurrence
  and **excluded from external ingest**. This closes the self-ingest loop.

### Lifecycle
```
occurrence created/needs-write  → create EKEvent (Busy), stamp AppItemID, save writeState
occurrence time/derived changes → update the linked EKEvent in place
occurrence deleted / skipped    → delete (or, for a skipped recurrence instance, EXDATE) the EKEvent
calendar event edited by user   → user wins: adopt their change, re-derive, re-arm
calendar event deleted by user  → treat as "skip/detach"; do not resurrect it
```

### Write-target calendar (verified constraint)
Free/busy is a **calendar-source capability**, confirmed by the verification harness: a local
calendar supports *neither* busy nor free, so `.busy` is silently dropped. The write-target
calendar must therefore be filtered to one where
`supportedEventAvailabilities.contains(.busy)` **and** `allowsContentModifications == true`
(subscribed/holiday calendars are read-only). If no calendar qualifies, fall back to
`.free`/`.none` and surface it. Let the user pick the target explicitly.

### Rules
- **Busy** on all written events (decision 5), *when the target calendar supports it* (above).
  A per-item **"don't publish / mark free"**
  escape hatch should exist so wake/wind-down needn't clutter or blot the calendar as busy
  overnight — deferred, but the model reserves `writePolicy: .busy | .free | .none`.
- **User edits always win.** A user-moved event updates its occurrence's resolved time; the
  app never clobbers a manual edit. (Conflict = "last human edit wins; app adapts.")
- **Derived events update, don't duplicate.** A shifted wind-down moves its one event.
- **No orphans.** Deleting an occurrence deletes its event; a rolling reconcile prunes any
  app-marked events whose occurrence no longer exists (e.g., after a crash mid-write).

### Re-arm triggers
`EKEventStoreChanged`, sleep-schedule change, a new/changed meeting, a cue/binding edit, a
manual "Re-plan," and the horizon rolling forward. Any of these → re-resolve affected
occurrences → apply exceptions/placement → update calendar writes → re-arm AlarmKit/notifs.

---

## 5. Identity for exceptions (defined now, used in L2)

Per-occurrence move/skip/add needs a stable key independent of array position:
`OccurrenceKey = (seriesID, slotID, date)`. L1 only needs to *define* this and stamp
`seriesID`; L2 adds the override/extra store that rides on top and is applied during
resolution, uniformly for authored recurrence and for local overrides of external items.

---

## 6. Explicitly out of scope for L1

- The flexible **placement algorithm** and "Re-plan" UX (L4).
- The **exceptions store** and "this one vs the series" edit flow (L2).
- **Tasks** ingest from Reminders (L3).
- Any **auto-reflow** (decision: manual only).

L1's deliverable is: one `Occurrence` type, the three source producers, the cue↔source
binding, and the write-back sync contract with round-trip identity. Everything else attaches
to this spine.
