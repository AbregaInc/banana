# Mail and Calendar performance, 25–26 November 2026

## Mail opening

The previous reader loaded and styled the entire conversation before publishing any body. In a deterministic regression test, suspending the older local read left the newest card empty even after its verification code appeared. The reader now publishes the newest missing card with its styles, then publishes the remaining bodies together. Navigation and cancellation still use the conversation generation. Downloads of missing bodies still follow the visibility and retry rules.

On the Mac, the first comparison opened synthetic threads from real SQLite index and blob stores. Both variants read the same prepared bodies and styled all their blocks. The table shows medians across 12 new-reader opens per workload, six in each of two processes per variant. Fixture preparation and the OS page cache are outside this comparison. The first open of each workload and the regeneration of evicted prepared HTML are reported separately in the data.

| Workload | First readable body before | First readable body after | All bodies before | All bodies after | Reads before first body |
|---|---:|---:|---:|---:|---:|
| 1 short message | 1.30 ms | 1.21 ms | 1.31 ms | 1.22 ms | 1 → 1 |
| 12 short messages | 5.26 ms | 3.65 ms | 5.27 ms | 5.17 ms | 12 → 1 |
| 64 messages, 14 paragraphs each | 46.29 ms | 15.80 ms | 46.31 ms | 45.68 ms | 64 → 1 |
| 1 large prepared HTML message | 39.84 ms | 36.79 ms | 39.85 ms | 36.80 ms | 1 → 1 |

This pair includes an independent change to verification-code extraction. On ordinary messages without authentication instructions or labels, the extractor can finish before searching for candidate codes. On the bounded negative case its median fell from 4.27 to 1.26 ms. ### Mail lists, labels and styling

Both native list adapters now share date formatters within a row update. On the Mac, building 100 rows with mixed dates took 1.49 ms median, down from 15.88 ms. At the 300-row sliding-window limit it took 3.15 ms, down from 48.50 ms. A single mixed-date row took 0.204 ms against 0.201 ms. The comparison created fresh presentations each pass and verified every displayed date. [First-use and repeat projection samples](mail-list-dates.json)

Opening a thread now fetches the account’s user labels referenced by its messages and pending changes. The complete read of a single-message thread with two applicable labels in a 3,000-label account took 0.36 ms median, down from 1.76 ms. The empty-catalog case moved from 0.30 to 0.33 ms. ### Layout work

The mobile layout used to compare each event with every other event twice to determine its visual end and the available space below it. The new calculation groups equal start times, finds same-lane successors in start order and tracks the lowest projected position in each horizontal span. It preserves the repeated hour at a daylight-saving transition, strict later-start comparisons, optimistic move dates and the duplicate-identity fallback. Each update owns its own geometry.

On the busiest day generated by the varied 1,000-events/day fixture, 1,900 placements included overnight events. Neighbor preparation fell from about 20 ms to 2.4 ms. The final reference comparison covered 450 geometry cases across widths, zoom levels, daylight-saving boundaries and densities. Whole-frame duration also includes view layout, drawing and presentation. [Raw samples, checks and process memory](neighbors.json)

## Mail work while another screen is open

A silent push or a search from the shell could construct a Mail session while Calendar stayed visible. The session initializer started the foreground Mail engine, which kept polling after the push finished. Mail now starts foreground work when its first screen appears and stops when its last visible window leaves. Cached search and the bounded push still work while Mail is offscreen.

In the same-binary comparison, creating the session made one unsolicited feed request before the push. The push made one requested call. Over the next two simulated minutes the old lifecycle made four more unsolicited calls. With the visibility change, only the requested call ran. Opening Mail then started foreground sync. In a separate 15-minute outage with 181 pushes, the failing account made eight attempts, the healthy account answered all 181, and a pending star survived reopening the store and was confirmed with one provider write. These tests use a real SQLite store and fake providers. [Request counts, scenarios and test results](mail-foreground-ownership.json)

The physical iPhone repeated the foreground-activation comparison across four three-minute intervals with a healthy and a failing in-process provider. Eager activation made 16 provider calls in each trial and consumed 71 and 57 ms of process CPU. Offscreen startup made two requested calls in each trial and used 2.6 and 2.1 ms of CPU. Process interrupt wakeups fell from 40 and 23 to six and four. The whole-device power ranges overlapped, and the providers used no network. [Physical iPhone requests, process counters and battery readings](mail-offscreen-physical.json)

The draft worker also read an empty outbox every 30 seconds while Mail was active. A clean queue now waits for a durable edit. A saved draft held for sending wakes at its deadline.
