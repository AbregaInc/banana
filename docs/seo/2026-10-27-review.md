# Banana website: SEO, answer discovery and publishing review

Reviewed October 27, 2026. Scope: `bananatheapp.com`, its `www` alias, existing public
home/privacy/terms/support pages, and the new blog, article, About page, feed and sitemap.
This is a technical/content review with public HTTP probes and local browser evidence.
It does not establish Google/Bing indexation, rankings, organic demand or AI citations.

## Result and priority

The site already had a useful foundation: static HTML, a single clear product, a canonical
on each existing substantive page and self-hosted fonts,
responsive layouts, explanatory FAQ text, and a true 404 with noindex. The gaps were
publishing, discovery metadata, current feature descriptions and verifiable publisher context.

## Publishing and new-page acceptance

Posts are authored in `LandingPage/content/posts/*.md`, with TOML metadata. A missing explicit
`draft` field fails the build; `draft=true` or future dates are excluded from HTML, archive,
RSS and sitemap. Converting a previously published post back to draft removes its generated
page. The preview goes outside `site/`, includes drafts, and adds noindex and a visible notice.
It is not an authenticated CMS and must not be exposed publicly for confidential drafts.

The generator uses **markdown-it-py 4.0.0**, a maintained CommonMark implementation with an
MIT license, rather than a custom Markdown parser. The lock pins its dependency and hashes.
Raw HTML and executable Markdown links are disabled. Templates escape metadata separately
for HTML and JSON-LD. Sized image support is deliberately required before inline images can
be added; unsized Markdown images fail. All live editorial text is HTML before JavaScript runs.
No browser runtime framework, database or third-party script was added by this change.
Cloudflare injects its pre-existing Web Analytics beacon into some live responses (observed
with the audit user agent, but not the default curl response). The source has no such script;
local Lighthouse does not cover that edge injection. Check its dashboard configuration and
keep the corrected website-analytics disclosure aligned with what is enabled.

For every new article:

- Answer a specific reader question in the title and opening paragraph. Include an actual
  example and distinguish current behavior, device limits, required permissions and known bugs.
- Use a genuine byline/profile, real publication/edit dates, unique description, stable URL,
  meaningful h2 headings and links to relevant product/help/privacy pages.
- Verify product claims against released behavior. Link external factual claims to primary
  sources. Do not turn “Busy hides the copied title” into a promise that Google permissions
  or direct event invitations cannot reveal details.
- Add first-hand screenshots or measured examples only when available and permitted. Give
  images dimensions, useful alt text and a realistic byte budget. No synthetic proof/results.
- Run publishing tests, regenerate, run the site checker, then inspect mobile/desktop and
  JavaScript-disabled rendering. A schema parse check is not a Google Rich Results test.
- Keep unpublished material out of the live folder. Publish with `LandingPage/publish.sh`;
  commit the source and generated output together. Do not change dates just to suggest freshness.

Full instructions: [website README](../../LandingPage/README.md).

## SEO and content intent

Banana is an ambiguous name (fruit, other software and an app). Concrete category and platform
language matters more than repeating “Banana” everywhere. The home page targets the umbrella
intent **Google Calendar daily planner for iPhone/iPad/Mac**. The first guide answers the
narrower **Busy blocks across work and personal Google calendars** question, with limitations.
The blog archive is discovery/navigation; it is not another competing product landing page.

Suggested next editorial subjects, after checking released behavior:

| Reader question | Page purpose | Proof/limits to include |
| --- | --- | --- |
| How do I stop work and personal Google calendars from double booking? | Expand the existing Busy guide only when a concrete setup walkthrough is available | Actual Settings steps, ownership/write permissions, time zones, multi-account example |
| Can I mute one shared calendar without hiding it? | Separate notification/visibility guide | Real iOS/Mac screenshots; explain Google sharing is a different control |
| How does travel time reserve space on my calendar? | Travel guide | Actual supported modes, locations, look-ahead window and failure states |
| What works on iPhone, Mac, iPad and Watch? | Platform guide | Current device/OS support; Apple silicon only; phone/Watch dependencies |
| What information does a guest receive? | Sharing guide after the unresolved sharing review | Account permission matrix and actual guest preview; do not publish assumptions |

No keyword-volume or competitor-ranking study was available here; these are product-informed
editorial hypotheses, not measured search-demand claims. Avoid generating interchangeable
“best planner” pages, unsupported competitor comparisons or broad health-advice content.
Useful firsthand setup guides and documented fixes are stronger material for this product.

## AEO / GEO / AI discovery

The practical work overlaps SEO: clear answers, crawlable HTML, descriptive links, consistent
entities, real examples, accurate scope, current documentation and easy source attribution.
Google's current guidance does not require special AI markup or an `llms.txt` file; this review
therefore does not add one as a ranking tactic. Answer-oriented sections serve readers first.
The app/organization schema describes visible claims; rich-result eligibility is not promised.
Software-app markup intentionally omits offers/review data that cannot be truthfully supplied.
No FAQ rich-result claim is made.

`robots.txt` retains the existing wildcard allow policy. That includes search and training
crawlers; this change does **not** make a new training opt-in/opt-out decision. OpenAI documents
OAI-SearchBot (search) separately from GPTBot (training). A future training-policy decision can
be made independently of search discovery. Browser/UA probes only show public responses to
those strings; they do not establish access from verified crawler IPs or absence of WAF rules.

Do not use private calendar/account pages as SEO landing pages. The cloud app's authenticated
content and API are a separate indexing/access-control review; this change does not modify
Service or treat robots rules as an authorization boundary.

## Measurement and remaining operator work

1. Verify the domain property in **Google Search Console**, submit `/sitemap.xml`, inspect the
   home/blog/article rendered HTML and canonical selection, check Page indexing/Crawl stats,
   and review the current generative-AI inclusion controls/reports exposed for the property.
   No new account/token/ownership change was performed here.
2. Verify/import **Bing Webmaster Tools**, submit the same sitemap and inspect URL indexing.
   IndexNow can follow if publishing volume justifies it; it is not a prerequisite for a
   one-post static blog. No unsupported indexing API call was made.
3. In Cloudflare, enable **Always Use HTTPS** (HTTP currently serves 200) and create a **Redirect Rule** matching host `www.bananatheapp.com` and redirect
   to the apex, preserving the complete path and query. Test `/`, an article and `?utm_source=`.
   Do not add a catch-all relative static redirect that loops or redirects the apex to itself.
4. Monitor non-branded impressions/clicks and article-specific queries over several weeks,
   actual TestFlight/outbound conversions if instrumented with an approved measurement plan,
   and real AI referrals/citations where visible. No analytics or consent-sensitive tracking
   script was added silently; the existing Cloudflare Web Analytics beacon is disclosed. No ranking/citation guarantees follow from deployment.
5. Review available CrUX/field Core Web Vitals when sufficient real traffic exists. Lab
   Lighthouse results are a local single-run diagnostic; they are not field data, native
   120Hz performance acceptance or a controlled page-speed improvement claim.

## Evidence and reproduction

- `evidence/live-before.json`: public HTTP status, canonical/meta, missing sitemap/new routes,
  alias behavior, HTTP response and named-agent probes before deployment.
- `evidence/live-after.json`: same probes after deployment, including redirect and XML MIME types.
  `live-after-first-probe.json` is retained: its exact-byte comparison failed because Cloudflare
  added its existing analytics beacon. The rendered page metadata was already correct; this
  was not treated as a content or indexing failure. Final content checks account for the provider injection.
- `evidence/layout.json`: 21 page/viewport cases (375/768/1440) plus article without JavaScript.
  Covers status, horizontal overflow, unique h1/main, images, browser errors and article navigation.
- `evidence/blog-{index,article}-{375,1440}.png`: actual headless rendered previews.
- `evidence/lighthouse-home.json.gz`: original homepage check with accessibility contrast failure.
  `lighthouse-home-final.json.gz` retains the corrected check; blog/article reports are separate.
- `evidence/validation.txt`: publishing/site checks and build determinism output.

Validation: seven publishing tests pass; 22 layout/navigation/no-JavaScript cases pass;
seven indexable pages pass the site checker. Final local mobile Lighthouse scores for home,
blog archive and article are **100 performance / 100 accessibility / 100 best practices /
100 SEO**. The first homepage candidate scored 95 for accessibility; its failure is retained.
The corrected byte check reports 169 KB first screen / 187 KB whole page under the unchanged
320 KB / 900 KB limits. These numbers include the previously omitted room images.

The separate production-home run (`lighthouse-live-home.json.gz`) reports **97 performance /
100 accessibility / 100 best practices / 100 SEO**, LCP 1.8 seconds, CLS 0 and total blocking
time 0 ms. It has no runtime errors/warnings. This includes normal network delivery, unlike
the local run, but remains one emulated lab observation. There is no field-data or causal
speedup claim. Raw live evidence explicitly flags the provider beacon; final content parity
normalizes only that identified injection. All ten tested public documents match source bytes.

Website deployment: `eddcb843-adaa-4fb7-b874-48bf2ef4c184` (initial); any final content-only
deployment is recorded in `evidence/deployment.json`. Only the public website is deployed;
no app/Service deployment or Apple submission is part of this change.

Lighthouse 13.6.0, Chromium headless shell 143 / Playwright 1.57.0, local Cloudflare Workers
assets server, mobile emulation/default Lighthouse throttling. No native application or
physical device was used. Full Lighthouse JSON is retained losslessly as `.json.gz` (read with `gzip -dc FILE`);
`lighthouse-summary.json` provides a readable score/metric summary. See report JSON for actual browser version, configuration, scores
and limitations. Existing animation, font policy and cache TTLs are unchanged.
