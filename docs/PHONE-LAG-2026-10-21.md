# Phone lag investigation, October 21

Private device evidence is retained outside Git under
`~/Library/Logs/Banana/PhoneLag-20261021/`. It includes playback logs, diagnostic
events, the process inventory and two timestamp reproductions. No phone restart
or reinstall was needed to capture these files.

## Confirmed defects

The workout review watermark was persisted as Unix seconds. Converting a real
Health workout's end time to Unix seconds and back rounded it downward by
0.119 microseconds. Every activation consequently treated that same workout as
new. New watermarks now persist as `Date`; the comparison tolerates one
millisecond for legacy values. Genuinely newer workouts still open their review.

Notes compared local sub-millisecond timestamps against their own rounded
millisecond sync echoes. Ten of the 22 captured notes had local clocks later
than their own echo. The logs repeatedly reported kept-own notes and subsequent
uploads. The note store and SQLite write guard now compare at the canonical
wire precision. An adapter regression reproduces 100 reuploads under the former
policy and zero under the corrected policy; repository coverage checks that
equal-clock resolved edits persist and genuinely older edits still lose.

## Remaining performance diagnosis

The captured phone process used approximately 71–78% CPU with serious thermal
pressure. Calendar write-back spans reached 92 seconds and included Google rate
limits. The phone main app was still build 68 (31-day horizon), while Mac main
was build 69 (90-day horizon). This is a possible source of cross-device calendar
churn, not a proven cause of the podcast screen lag. Mac main was quit to stop
its longer-horizon reconciler while the phone update is held.

Time Profiler failed to attach, first by process name and then by PID with a
device boot timeout. There is no usable CPU stack recording and no measured
before/after podcast interaction result. The persistent performance gate also
reports an unmeasured environment mismatch. The clock checks are correctness
coverage, not a UI performance certification.

## October 22 recovery and phone update

With the phone unlocked, app-container recovery succeeded. A USB connection also
allowed `idevicesyslog archive` to recover the recent system log archive. Private
artifacts are in `~/Library/Logs/Banana/PhoneLag-20261022/`.

The system logs explicitly report four hangs in build 68 during the live
reproduction: 260 ms, 310 ms, **3,960 ms** and **1,010 ms**. These exceed the UI
contract. They establish a real stall, but contain no sampled blocking stack.
The contemporaneous app log still shows the note being rejected and uploaded
about every six seconds. CPU was approximately 2.5% with nominal thermal state
in the later foreground samples: the earlier thermal incident alone cannot
explain all of today's reported lag.

The overnight memory-pressure report lists Banana as suspended, with the same
PID still present in the morning. It does not establish that Banana was killed.
Time Profiler retries over Wi-Fi and USB failed with process lookup, connection
or device-boot timeout errors. Keep these failed recordings; they are not
performance passes.

Main iOS build **70**, source `c521a11f`, compiled successfully, passed strict
bundle signature verification, and was installed after the hold expired. A
fresh device app inventory verifies `com.boris.banana` build 70. The artifact hash
and installation results are retained privately. This records only the main
iPhone update; it does not claim a Beta, iPad, Mac, Watch or TestFlight rollout.

The user verified that the workout summary stays dismissed after backgrounding
and reopening build 70. The podcast lag persists. This rules out treating the
note-loop repair as a complete podcast responsiveness fix. The user also reported
that manual Previous/Next episode pagination is awkward and laggy. Build 70 does
not change that UI. Build 71's continuous browsing work subsequently passed
the model regressions and targeted scrolling/settings UI tests. The user retested
it on the iPhone and reported responsive scrolling and absent filtered voices.
No sampled stack proving the original blocking call was recovered, and the
instrumented frame/input budgets remain unmeasured.
