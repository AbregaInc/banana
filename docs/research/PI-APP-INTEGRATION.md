# Pi inside Banana's normal app

25 October 2026. Implementation is in the isolated Pi worktree; acceptance reports must be checked separately. The installed main/Beta apps and Apple review state are outside this work.

Pi uses Banana's real app graph, existing pages and stores. Since the 28 October UX pass, the shared workspace is the phone/iPad home; existing pages live behind Browse. The Mac starts in Workspace with category rows under a collapsible Browse group, and retains the Ask Banana shortcut (Command-J). Its local app graph initializes the shared Plan dependencies. The build retains its separate files, preferences, Google credential service and peer namespace. It does not migrate Beta's SDK session, revoke its OAuth grant on Pi disconnect, enable production cloud polling, or start automatic calendar write-back.

The public `banana-workspace` Pi extension owns a conversation-scoped document. Its tools prepare new meals/events, search local app data and offer native page navigation. Native code validates every descriptor and resolves calendar dates; it supplies a real catalog/correction match or an explicitly manual food row. The model never supplies authoritative nutrition values or executes app capabilities. Draft identities, revisions and descriptors survive SQLite reopen. A late generation cannot overwrite a dismissed or newer draft. Model revision arguments are replaced by captured host metadata. No Pi core implementation was changed.

The existing `FoodTextCaptureView` and `NewCalendarEventSheet` review and save drafts. The 26 October UX pass embeds their shared fields directly into new Pi meal/event workspaces; the 28 October pass also embeds meal-copy review. Entry points from existing app pages retain their sheet presentation. There is no second editor or parallel calendar writer. Meal saves use the existing stable-ID native commit. Reviewed event input carries the draft UUID through the existing pending-write store. Google event creation uses a client-generated ID plus app-private operation/payload markers; on a duplicate-ID response, only a matching operation/fingerprint is accepted as acknowledgement recovery. A changed payload or unrelated collision fails. This follows Google's documented [client-generated event IDs](https://developers.google.com/workspace/calendar/api/guides/create-events) and [409 duplicate response](https://developers.google.com/workspace/calendar/api/guides/errors). The network recovery branch has not yet been exercised against a live Google account; do not conflate helper tests with a real remote write.

Local search covers notes, meals, recorded workout summaries, routines, podcast titles and the loaded plan, with up to six results per section and 30 total. Notes, podcasts and workouts route into existing navigation stacks; meals select their actual logged date. Other results open the relevant app page. This is bounded local text matching, not full-text/semantic search of every app object or podcast transcript. The model receives a bounded result preview; the native card retains the result list. Meal and note results can now expand into current native record details without opening another page. Other results keep their direct page links.

Before reporting completion, require the real-model workspace flow plus existing agent/nutrition regressions, visible full-shell navigation and native editor/cancel checks, and compilation/verification of the touched mobile routes. A prepared event, a queued save and a calendar-confirmed event are different outcomes and must be reported distinctly.

Real-model Mac workspace/nutrition/general flows pass; physical iPad Apple-model workspace verification passes in `pi-apple-host-results/ipad-integrated-workspace.json`. Mac full sidebar and real meal data were observed manually. The iPad simulator passed normal launch, shared meal review/cancel/restore, shared event review/cancel/restore and global meal search into Nutrition. The meal-save UI regression and its UUID-case fix are retained separately.

Physical iPad XCTest could not enable automation, so it establishes no physical UI acceptance. The final Mac manual editor recheck could not start because CUA's native pipe failed. No remote calendar creation/retry acceptance is claimed. These are scoped implementation/functional checks, not certification that every app feature, lifecycle condition or memory tier is accepted. The final retained Mac workspace run had a 99.54-second meal generation despite passing functionally; consult the inference selection protocol rather than treating success as a latency result.
